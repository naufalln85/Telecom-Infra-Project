Overview Arsitektur — IoT Platform (Riset & Pengembangan Non-Skripsi)

Dokumen ini adalah rujukan bersama untuk 4 mahasiswa riset yang mengembangkan modul berbeda dari satu IoT Platform. Setiap mahasiswa punya file tugas terpisah, tetapi WAJIB membaca file ini dulu sebelum diskusi dengan Gen AI apa pun, supaya tidak ada modul yang keluar dari desain yang sudah disepakati.

Tujuan platform: multi-tenant IoT platform dengan model freemium, mendukung banyak protokol komunikasi, punya AI model serving dengan sandbox, dashboard realtime, alerting, dan logging performa yang bisa dipakai mahasiswa lain untuk riset TA mereka (bukan cuma internal QA).

Keputusan arsitektur yang SUDAH FINAL (jangan diubah tanpa diskusi ulang dengan tim)

  1. Database: PostgreSQL untuk metadata (account, project, device, config, rules), TimescaleDB (extension di atas Postgres yang sama) untuk data telemetri time-series. Bukan kombinasi SQL+NoSQL generik. Alasan: data telemetri adalah write-heavy, time-indexed — TimescaleDB dirancang untuk pola ini, sementara NoSQL dokumen tidak memberi keuntungan nyata di sini.

  2. Event bus internal: Redis Streams, bukan MQTT broker dijadikan backbone internal. MQTT broker (mis. EMQX/Mosquitto) tetap dipakai di sisi gateway untuk device yang connect via MQTT, tapi begitu event masuk sistem, dia dinormalisasi dan dipublish ke Redis Streams supaya banyak consumer (storage, AI, websocket, alerting) bisa baca event yang sama secara independen lewat consumer group.

  3. WebSocket fan-out: wajib pakai Redis Pub/Sub sebagai backplane di belakang WebSocket gateway sejak awal, walau saat ini baru 1 instance backend. Ini supaya saat backend di-scale ke banyak instance nanti, tidak perlu migrasi ulang.

  4. AI model serving: hanya menerima format ONNX (operator whitelist), dijalankan di sandbox terisolasi (gVisor atau nsjail), bukan container Docker biasa yang berbagi kernel host. Ada resource limit keras: CPU, memori, timeout, tanpa akses network keluar dari sandbox.

  5. Alerting: threshold sederhana per data point (bukan kondisi majemuk AND/OR), tapi WAJIB ada parameter cooldown/debounce per alert untuk mencegah spam notifikasi saat nilai berosilasi di sekitar threshold.

  6. Performance logging: platform mencatat timestamp di setiap hop SISI SERVER SAJA (gateway terima → masuk queue → worker proses → tulis DB → push ke dashboard). Platform TIDAK mengklaim mengukur delay device→server yang akurat, karena itu butuh jam device tersinkron NTP yang di luar kendali platform. Log ini diekspos lewat API export (CSV/JSON) supaya mahasiswa lain bisa olah sendiri untuk kebutuhan riset TA mereka.

  7. Tenant isolation: shared schema dengan kolom tenant_id/project_id sebagai filter di setiap tabel, bukan schema-per-tenant atau database-per-tenant.

  8. Container: Docker untuk servis internal (gateway, backend, dashboard) — ini aman dan cukup. Sandbox tambahan (gVisor/nsjail) HANYA untuk AI inference karena itu kasus untrusted code execution dari user.

Batasan yang wajib didokumentasikan (bukan bug, tapi keputusan desain)

  • Delay device→platform TIDAK diukur akurat oleh platform kecuali device sudah NTP-sync sendiri. Ini tanggung jawab pengguna platform (mahasiswa TA lain), bukan platform.

  • Alerting hanya threshold tunggal per data point, tidak mendukung kondisi majemuk di versi ini.

  • DB eksternal (selain Postgres/Timescale bawaan) hanya lewat API endpoint di fase 2, tidak ada di MVP.

Cara pakai file ini saat diskusi dengan Gen AI

Setiap mahasiswa: sertakan file overview ini SEKALIGUS file tugas modul masing-masing di awal percakapan dengan Gen AI kalian. Ini mencegah Gen AI menyarankan arsitektur alternatif yang sudah diputuskan tim (misalnya menyarankan MongoDB, atau menyarankan Docker polos untuk AI sandbox) — kalau itu terjadi, itu tanda AI belum baca konteks ini, bukan tanda keputusan tim salah.
